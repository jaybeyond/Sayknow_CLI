한 줄 결론 (진단 시점)
TypeSafe는 코딩에 관여하지 않는다. 현재 쓰이는 곳은 워크플로 라우팅 한 군데뿐이고, 그 자리에서는 정확도를 올린다. 그런데 배선 결함이 하나 있다 — SKC 자체 TUI에서 키워드가 맞는 프롬프트는 의미 판단도 활성화도 건너뛴다. 오늘 추가한 한국어 키워드 8개가 SKC TUI에서는 죽은 코드다. 기본값이 off라 사용자 영향은 없지만, 켜기 전에 반드시 고쳐야 한다.

3. 배선 결함 — 지금 고쳐야 하는 것

SKC TUI에서 키워드가 맞는 프롬프트는 활성화되지 않는다. 수정됨

사실관계를 순서대로 놓으면:

  1. UserPromptSubmit 훅(skc codex-native-hook)이 키워드 활성화를 담당한다. 그런데 이 훅은 ~/.codex/hooks.json에 설치되는 Codex CLI 연동 전용이다. SKC 자체 세션/TUI에서는 발사되지 않는다 (코드베이스에서 UserPromptSubmit을 참조하는 곳은 훅 구현과 설치 스크립트뿐).
  2. SKC TUI에서 워크플로를 켜는 경로는 /skill:<name> 명시 호출뿐이었다 (agent-session.ts:7762). 일반 프롬프트의 키워드는 시스템 프롬프트 <routing>이 모델에게 알려주는 권고였지, 결정론적 활성화가 아니었다.
  3. 내가 넣은 #routeWorkflowSemantically는 if (detectPrimarySkillKeyword(text)) return; — 주석에 "deterministic stage already decided"라고 썼다. 이 전제는 Codex 호스트에서만 참이다.
  4. 결과: SKC TUI + decisions.enabled: true에서
    "실행 전에 합의된 계획부터 세워줘" → 한국어 키워드 합의된 계획 히트 → return → 의미 판단 안 함 → 활성화 안 함.
    키워드를 추가하기 전에는 이 문장이 의미 판단으로 가서 활성화됐다. 키워드 추가가 이 경로에서는 퇴행이다.
평가 스크립트의 "hybrid 100%"는 출시된 동작이 아니다. 수정됨
scripts/eval-skill-routing.ts는 keyword ?? semantic을 계산한다 — 두 단계가 합쳐졌을 때의 이상적 결과다. 실제 agent-session.ts는 키워드 히트 시 아무것도 하지 않는다. 내가 "하이브리드(출시본)"라고 표기한 수치는 측정 대상과 출시 코드가 달랐다. 이 보고서에서 정정한다.

적용 결과: 라벨을 keyword only (Codex hook) / semantic only (SHIPPED) / keyword+semantic (upper bound)로 바꾸고, 미스 목록도 출시 구성 기준으로 보고하도록 고쳤다.

두 호스트가 서로 배타적이라 이중 활성화는 없다 — 그건 확인했다. 문제는 이중이 아니라 누락이다.

수정 — 결정이 하나 필요하다

// 지금
if (detectPrimarySkillKeyword(text)) return;
const skill = await this.#semanticSkillRouter(text);

// 안 A — 키워드도 SKC TUI에서 결정론적으로 활성화 (Codex 훅과 동일 동작)
const skill = detectPrimarySkillKeyword(text)?.skill ?? await this.#semanticSkillRouter(text);

// 안 B — 키워드는 권고로 두고, 의미 판단만 활성화 (기존 SKC 동작 유지 + 의미 단계 추가)
const skill = await this.#semanticSkillRouter(text);   // 키워드 조기 return 제거

A는 "consensus plan"이 SKC TUI에서도 하드 활성화된다 — Codex와 동작이 같아지지만, SKC 사용자에겐 새 동작이다. B는 SKC의 기존 계약(키워드=권고)을 지키면서 의미 판단만 얹는다. 대신 키워드 히트 프롬프트도 매번 판단 호출이 나가 비용이 조금 는다.

적용 결과: 안 B를 채택해 if (detectPrimarySkillKeyword(text)) return;을 제거했다. 회귀 테스트 "a keyword hit no longer suppresses the semantic stage"로 고정 — 키워드가 맞는 프롬프트가 실제로 백엔드에 도달하는지까지 검증한다.

권고 근거: B. 활성화는 사용자에게 뮤테이션 가드·Stop 훅이 걸리는 강한 동작이라, 이미 있던 계약을 조용히 바꾸지 않는 쪽이 맞다. 키워드는 confidence 없이 발동하므로 오탐 시 되돌릴 신호도 없다.

보정돼 있다. 확신한 것(1.00)은 전부 맞았고, 유일한 오답은 스스로 "애매하다"고 표시했다. 다만 정답 최소(0.67)와 오답(0.71)이 겹친다 — 임계값 하나로 완벽히 가를 수는 없다. 그런데 겹치는 정답 쪽은 none이라, 폴백으로 보내도 손해가 거의 없다(다시 none이 나오거나, 워크플로를 안 켜는 안전한 실패).

따라서 confidence 게이트가 정당화된다. 적용됨 — MIN_CALIBRATED_CONFIDENCE = 0.75
confidence < 0.75 → 활성화하지 않음으로 두면 오답 1건이 잡히고 정답 1건이 같이 걸리는데, 그 정답은 어차피 "켜지 말자"였다. 실질 손해 0. 이걸 안 넣으면 TypeSafe를 쓰는 이유의 절반을 버리는 것이다.

5. "어떤 언어로 말하든 영어로 추론" 기능과의 관계

확인한 사실:

설정 키
reasoningLanguage: "off" | "english" (기본 off). 별도로 language(UI 언어, 현재 ko)
구현
system-prompt.md의 지시문 3줄. {{#if reasoningLanguageEnglish}}로 렌더
내용
"Reason through development in English. Keep user-facing answers in the language the user used."
번역 파이프라인?
없다. 프롬프트는 한국어 그대로 Claude에 간다. Claude가 사고만 영어로 하라는 권고다

충돌 여부: 없다 — 다만 이유를 정확히

  • 두 기능은 다른 레이어다. reasoningLanguage는 Claude 시스템 프롬프트 템플릿 플래그. 판단 라우팅은 Claude 턴 이전에 상태 파일을 쓰는 단계. 서로 읽지도 쓰지도 않는다.
  • 판단 라우팅은 reasoningLanguage를 참조하지 않고, 참조할 필요도 없다. TypeSafe는 한국어 원문을 받는다.
  • "영어로 번역해서 TypeSafe에 보내면 정확도가 오르지 않을까" — 이론상 그렇다(문서가 영어 우위를 명시). 하지만 번역에 모델 호출이 하나 더 필요해 이 기능의 존재 이유(싸고 빠름)를 무너뜨린다. 한국어 89%를 받아들이고 confidence 게이트로 방어하는 게 맞다.
결론: 배선이 꼬이지 않았다. 두 기능은 독립이고, 켜고 끄는 조합 4가지 모두 서로 영향 없이 동작한다. 유일한 접점은 "둘 다 한국어 사용자를 위한 기능"이라는 목적뿐이다.

7. 개선 방향 — 우선순위

P0 · 켜기 전에 반드시 완료

  1. §3 배선 수정 — 안 B 권고. 키워드 조기 return 제거. 테스트: SKC TUI 경로에서 한국어 키워드 프롬프트가 활성화되는지 실제 세션으로 검증 (스텁 아님).
  2. 평가 스크립트 정직화 — "hybrid (shipped)" 라벨 제거. 출시 코드가 실제로 하는 것과 이상적 결합을 분리해서 보고.
  3. confidence 게이트 — calibrated:true인 답에 한해 confidence < 0.75 → 활성화 안 함. llm 백엔드(calibrated:false)는 게이트 없음(숫자가 의미 없으므로).

P1 · 켜고 나서

  1. 실사용 오탐 관찰 — 벤치 23문항은 내가 쓴 문장이다. 네가 실제로 치는 프롬프트에서 워크플로가 원치 않게 켜지는지 며칠 본다. 오탐 1건이 미스 10건보다 나쁘다.
  2. 임계값 재적합 — 실사용 로그가 쌓이면 0.75를 데이터로 정한다. 지금은 10문항 근사.
  3. criteria 보강 — 오답 1건("추측하지 말고…")은 deep-interview 설명에 "정보를 캐묻는 요청" 계열을 추가하면 잡힐 가능성. 재측정 필요.

P2 · 확장 검토

  1. 인젝션 스크리닝 — fetch 결과에 noul 2개(injection_attempt, instruction_shaped). 병렬이라 체감 0. 경고 표시만, 격리는 confidence ≥ 0.9에서만.
  2. 컨텍스트 필터 — 검토는 하되 "버리기"가 아니라 "순서 재배치"로 시작. 관련 없는 청크를 뒤로 보내는 건 틀려도 안전하다.

하지 말 것

  • TypeSafe를 packages/ai 채팅 프로바이더로 등록 — 고를 수 없는 모델이 선택기에 생긴다 (이미 안 하고 있음, 유지)
  • 번역 후 TypeSafe 호출 — 호출 하나가 더 붙어 존재 이유가 사라진다
  • 확률을 프론티어 모델에게 쓰게 하기 — 정확도 0.35로 무너진다(이미 회피, 유지)
  • "코딩이 좋아진다"는 기대 — 구조적으로 불가. 이 기능의 값어치는 한국어로도 워크플로가 켜진다에 있다
